### R5-1 的具体处理

- 核对实验脚本中计时器的起止位置，以及表生成、加载、查询各阶段是否计时；不能把“表是预计算的”直接等同于“预计算时间未计入”。
- 用简短正文解释三组 nominal PT 差异，明确相同 M、N 不表示相同模式生成配置或同一场景 realization。
- 若表准备时间未计入，明确这是在线规划时间，并说明离线准备开销及复用范围；若没有保存离线耗时，如实说明，不补造数值。只有确需报告该耗时且现有记录不足时，才安排针对性的计时。

### R5-2 的具体处理

这是最需要先核实实现的一条。查实际 quick-pass 分支、缓存键和返回值，分别回答：

1. 复用的是接触模式、可行性结论，还是整段状态转移？不要将 warm start 与免 rollout 混为一谈。
2. 目标物体形状、质量、摩擦等参数，机器人配置/力限、接触布局、推动方向与持续时间，以及初始位姿/速度中，哪些必须一致，哪些允许通过坐标变换复用？这些都是核查项，不是已确认的实现条件。
3. 当前场景是否重新检查机器人及物体扫掠区域、其他物体相互作用和接触前可达性？
4. 不运行 rollout 时，如何计算或复用 s′、δT、δJ，并更新未移动物体、机器人和 WCCG？
5. 哪些变化会使验证失效并退回完整 rollout？

以真实实现组织一段简洁说明。若实现采用近似，需如实限定；若发现实际缺陷，另行确定修复及受影响结果的复核范围。当前仓库的 `code_related/` 只有部分实现文件，完整 quick-pass 执行路径尚未定位。

### R5-3 的具体处理

在正文补充：各扰动条件复用相同的十个基础场景，因此 160 个扰动 trial 不代表 160 个独立场景；每次只扰动一类参数，不覆盖多参数联合误差；baseline 每条件五个种子，且 nominal 成功率为 3/5，而本方法为 10/10。因此比较反映当前测试设置下的端到端表现，不能直接解释为归一化后的鲁棒性退化差异。

### R5-4 的数字口径

从 `data/physics_mismatch/raw_results.csv` 按成功 trial 重算：

| 数据范围 | 成功数 / trial 数 | 成功 trial 的平均执行时间 |
|---|---|---|
| Nominal | 10/10 | 104.7 s |
| 全部扰动（±20% 和 ±40%） | 156/160 | 108.9 s |
| 仅 ±40% 扰动的八个条件，合并成功 trial | 78/80 | 114.3 s |
| 仅 force-limit ×0.6 | 9/10 | 159.6 s |

额外核查发现，旧回复 Table R2 中的 115.0 s 可以通过“先算八个条件各自成功 trial 的均值，再将八个均值等权平均”复现（115.0266 s）。直接合并 78 个成功 trial 得到 114.2606 s。因为有两个条件各只有九个成功 trial，两种算法不完全相同。需确定并明确汇总定义，同时检查同一汇总行的 PT、ET 和 replans 是否采用一致的规则；若沿用“成功 trial 的平均时间”这一表述，应按合并成功 trial 的口径重新核对相关数字。

旧回复还应明确区分“±40% 汇总”和“force-limit ×0.6 下 159.6 s”，消除 `there` 指代不清。该汇总口径问题属于本次核查发现的额外一致性任务。

硬件的 77.1 ± 15.9 s 需追溯原始统计：若 15.9 为标准差，则明确写 mean ± standard deviation，并核对统计样本及是否仅包含成功 trial。不能将标准差解释为额外恢复时间，也不能无单独计时证据就把全部波动定量归因于滑移或力限。

### R5-5 的具体处理

核对硬件监测逻辑后，统一描述位姿误差阈值与接触失败、推动停滞、连通性失效之间的关系。如果这些事件通过位姿误差间接触发，应明确该关系；如果是独立触发条件，应列为并列条件并删除不恰当的“only”。保留实际采用的阈值，不添加未实现的监测机制。
